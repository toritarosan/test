## やりたい構想：参加型「リクエスト→検証済みカード」＋市民関心の可視化
サイト訪問者が「◯◯について知りたい」と投げると、しばらくして検証済みカードができる仕組み。
静的アーカイブを「生きた市民関心ボード」に進化させる。

### レイアウト案（左右分割）
- **左＝収録済み（検証済み・正式記録）**：現在の議題まとめ。AI生成＋`verify.py`＋人手承認を通った確定コンテンツ。
- **右＝リクエスト（生きた関心）**：訪問者が投げた話題。ここが市民の関心・トレンドの窓。
- **カードの“昇格”フロー**：リクエスト（右）→ 生成＋検証 → 人が承認 → 左に「収録」として移動。

### トレンド可視化（低リスクで“楽しい”部分）
- 生成物ではなく**リクエストそのものを集計**するのは原典照合の心配がなく安全。
  - 「今週よく聞かれた議題」ランキング／タグクラウド／「N人がこの話題を知りたがっています」等。
- 但し書きを明示：右側は「わざわざ聞いた訪問者」の関心であり、**市民全体の縮図ではない**。

## アーキテクチャ（静的サイトのままにする）
```
[① 依頼]  サイト or HF Space の入力欄「◯◯について作って」
   ↓（非同期・数分）
[② 生成＋検証]  コンピュート層（HF Spaces もしくは GitHub Actions）:
   1. 話題に関係する原典会議録を検索（RAG）
   2. POLICY.md に従いカードを下書き（LLM）
   3. verify.py で原典と機械照合  ← 必須ゲート。右側の生成物にも必ず適用
   4. 合格→採用／不合格→破棄 or 再試行／根拠なし→「該当なし・原典参照」
   ↓
[③ 反映]  合格カードを PR でリポジトリへ → 人が承認・マージ → Pages 再ビルドで公開
```
- **コンピュート層の候補**：
  - A. **HF Spaces**（ユーザーが挙げた案）：入力欄＋生成エンジン。秘密鍵・GitHubトークン保持可、PR作成も可。
  - B. **GitHub Actions のみ**：Issue/フォーム起点でCIが生成→PR。外部サービス不要・全部GitHub内で完結。
  - 推奨：A×B ハイブリッド（HFで聞く窓口＋生成、合格物はPRで戻して人手承認）。

## 新規に必要な部品（今は無い）
1. **RAG検索**：話題→関連会議録の特定（62本をチャンク化しベクトル検索。FAISS/Chroma等）。← 最大の新規開発だが定番技術。
2. **生成モデル**：Claude API または HF のオープンモデル。
3. **書き込み権限**：Space→リポジトリへ push/PR するための GitHub トークン（シークレット格納）。
4. **モデレーション（最重要）**：公開リクエスト欄は荒らし・誹謗・誘導（特定議員を貶める生成 等）が来る。
   不適切語フィルタ＋**公開前の人手承認**必須。リクエスト文の表示にも承認が要る。
   ただし削除・却下は「荒らし・誹謗・違法・スパム」に限定し、**内容の立場を理由に消さない**（POLICY §9-2）。
   検証・モデレーションを通ったリクエストは恣意的に選別せず公開する（取捨選択バイアスの排除）。
5. **コスト制御**：1リクエスト＝LLM課金。レート制限＋類似リクエストのキャッシュ/集約。
6. **トレンド集計**：リクエストのログ集計・ランキング・タグ化。

## 正直な注意点（＝“非現実的か？”への答え）
- 技術的な難所は少ない（生成＋検証は既にある）。本当の勝負どころは **モデレーションとコスト管理**という運用面。
- 検証ゲートを右側にも必ず通すこと。飛ばすと今まで積み上げた正確性保証が崩れる。
- 初期はリクとが少なく右カラムが過疎になりがち → 運営側で種まき。

## おすすめの進め方（段階）
- **Phase 1（低リスク・すぐ楽しい）**：右＝リクエスト受付＋トレンド板（集計表示のみ）。生成はモデレーション待ち行列へ。
- **Phase 2**：承認された話題を verify.py で検証→カード化→人が承認→左に“昇格・収録”。
- 着手するなら **HF Space の最小プロトタイプ**（話題入力→検証済みカード1枚を表示）に、最初から右カラム（リクエスト＆トレンド板）を組み込む形が良い。
